# ADR-0001: 状態管理に Riverpod を採用する / コード生成の可否

- ステータス: Accepted
- 日付: 2026-07-28

## コンテキスト

本アプリは「非同期データの取得と表示（書籍検索・レビュー同期）」が中心である。
そのため状態管理には、以下が求められる。

- 非同期状態（loading / error / data）を型として統一的に扱えること
- UI から独立した場所（application 層）にロジックを置き、テスト時に依存を差し替えられること
- 不要な再描画を抑えられる購読の粒度を持てること

## 決定

**Riverpod（`hooks_riverpod` 2.6 系）を採用する。**
非同期状態は `AsyncValue<T>` で表現し、ロジックは `Notifier` / `AsyncNotifier` を
**手書きの型付きクラス**として実装する。DI は Provider のオーバーライドで行い、
テスト時にリポジトリをモックへ差し替える。

## 検討した代替案

### a. Provider(package:provider) / setState
UIとロジックの分離や非同期状態の型表現が弱く、テスト容易性で劣るため却下。

### b. Riverpod のコード生成（`@riverpod` + `riverpod_generator`）
当初はこれを第一候補とした（ボイラープレート削減・自動 family 化が魅力）。
しかし本リポジトリが固定している **Dart 3.11.5 / Flutter stable** の環境では、
`riverpod_generator 2.6.x` が推移的に依存する `analyzer_plugin 0.12.0` が、
このSDKで利用可能な `analyzer`（7.4.5 / 7.6.0）と API 非互換で、
`build_runner` のビルドスクリプト自体がコンパイルできない
（`analyzer` 6.x は Dart 3.12 で削除された `_macros` に依存するため 3.11 では導入不可）。

グローバルの Flutter/Dart を上げれば解消するが、それは環境全体に影響する変更であり、
このリポジトリ単体の判断としては採用しない。
**結果として、Provider 定義は手書きとし、コード生成は freezed / json_serializable
（`analyzer_plugin` に依存せず、最新版が正常にビルドできる）に限定する。**

このトレードオフを承知の上で手書きを選んだのは、
- 手書きの `Notifier`/`AsyncNotifier` でも型安全・テスト容易性・購読粒度の要件はすべて満たせる
- 生成コードが減ることで、レビュアーが実装を直接追える（本リポジトリの目的に合致する）
という利点があるためである。

### c. Bloc
学習コストと本題材の規模に対する記述量が過剰で、Riverpod の `AsyncValue` の方が
非同期状態の表現に簡潔。却下。

## 結果（トレードオフ）

- 得たもの: 型安全な非同期状態、テスト容易な DI、安定してビルドできるツールチェーン
- 諦めたもの: `@riverpod` によるボイラープレート削減（Provider を手書きする手間）
- 将来: Dart 3.12+ に上げられる環境では、`@riverpod` へ移行する余地を残す
  （Provider を機能単位でファイル分割しているため移行は局所的で済む）
