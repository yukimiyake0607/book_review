# ADR-0005: GitHub Actions による品質ゲート

- ステータス: Accepted
- 日付: 2026-07-28

## コンテキスト

個人開発でも実務同様、「壊れたコードを main に入れない」仕組みを機械化したい。
また、生成コード（freezed / json_serializable）はリポジトリにコミットしない方針
（ADR-0006）のため、CI 上で再生成してから検査する必要がある。

## 決定

**GitHub Actions で `analyze → custom_lint → format → test → build` の順にチェックし、
これを通過しないと main にマージできないことを品質ゲートとする。**

パイプライン（[.github/workflows/ci.yml](../../.github/workflows/ci.yml)）:

1. `flutter pub get`
2. `dart run build_runner build`（生成物を作る。`--delete-conflicting-outputs` は build_runner 2.15 で廃止され、衝突は自動解決されるようになったため付けない）
3. `flutter analyze`（`analysis_options.yaml` の厳格ルール）
4. `dart run custom_lint`（`riverpod_lint`。`flutter analyze` では検出できない Riverpod 固有の規約違反を見る）
5. `dart format --set-exit-if-changed`（対象は `git ls-files '*.dart'` = 生成物を除外）
6. `flutter test`（API はモックに差し替え、ネットワーク非依存）
7. `flutter build apk --debug`（ビルド可能性の担保。ubuntu ランナーで高速）

## 検討した代替案

### a. 生成コードをコミットして CI では生成しない
CI は速くなるが、生成物のレビュー・コンフリクトが発生し差分が汚れる。
「再生成できること」を CI で保証する方が健全と判断（ADR-0006）。

### b. iOS ビルドも CI に含める
macOS ランナーが必要で低速・不安定（署名の考慮も要る）。
ビルド可能性の担保は Android APK で足りるため、iOS は CI 対象外とし、ローカル確認に委ねる。

## 結果（トレードオフ）

- 得たもの: main の常時グリーン、生成物の再現性、フォーマット/静的解析の機械的強制
- 諦めたもの: CI 時間（毎回 build_runner を回すぶん増える）、iOS ビルドの自動検証
